Trustworthy AI

EvoGuard

Evidence-driven control for AI-assisted code changes

github.com/modarresi1913/Evoguard

Maturity: Self-deployable template; reference implementation.

A context-aware gate between AI code generation and your main branch. Every AI-touched pull request is evaluated against the codebase's history, contracts, dependencies, tests, conventions, and security constraints — and either explained or blocked before merge.

Problem: AI-generated code reaches main with no inspectable chain of evidence. EvoGuard asks: what would it take to make every AI-touched change reviewable before merge?

New Computing Substrates

OrganoidOS

Open operating-system specification for biological neural computing

github.com/modarresi1913/OrganoidOS

Maturity: v0.1 stable spec + L0 reference emulator (CI green). v1.0 target: multi-vendor conformance.

An open operating-system layer for biological neural networks — cultured cortical organoids, MEA-coupled cultures, and the in-silico models that approximate them. Ships a versioned specification and a reference emulator. No biological result is claimed.

Problem: biological neural networks exhibit properties no current silicon substrate replicates, yet there is no shared OS layer for experimenting with them. OrganoidOS proposes one — as an open, forkable specification.

Trustworthy AI · Agents

Neuro-Continuum

An experimental architecture for context-adaptive, safety-aware AI interactions

github.com/modarresi1913/neuro-continuum-ai

Maturity: Experimental architecture + browser demo. The core hypothesis is explicitly falsifiable.

Estimates probabilistic interaction states from observable signals, then adapts the response policy. Every number in the demo is labelled ESTIMATE, never DIAGNOSIS — the project deliberately rejects human classification as a goal.

Problem: stateless AI treats two users with identical prompts identically, even when their interaction states differ. The architecture explores whether context estimation can improve interaction quality — and surfaces cases where it does not.

Research approach

A working method, not a guarantee

How the work moves from a question to something inspectable. These are principles that guide each project — not proof that every project has completed every stage.

  1. Question

    Start from a falsifiable question, not a conclusion. Say what would have to be true for the idea to fail.

  2. Specification

    Write the idea as an open spec: terms, interfaces, invariants, conformance levels. Make it forkable.

  3. Prototype

    Build the smallest implementation that can be wrong. A reference emulator counts; a slide deck does not.

  4. Evaluation

    Run it against a benchmark designed to surface failure — including the failure the team hoped not to find.

  5. Revision

    Publish what changed and why. Specs are versioned; abandoned directions are documented, not deleted.

A project can sit at any stage for a long time, and revising a specification is not failure — it is the method working as intended.
